# LingFlow
多Agent协作工作流（目前仅适配DSH）

LingFlow 是独立运行的 Windows 桌面协作工作台，使用 DSH 会话，保留快速模式。开发负责票内验证，高风险由独立审查者审查，低、中风险的免审实施票由主控完成独立验收检查。主控核对证据和收口，用户在工作台记录业务验收。

支持 Windows x64。源码安装需要 Node.js 24+；Windows 便携版解压完整目录后运行 `Start-LingFlow.cmd`，桌面界面无需另装 Node。团队协作需要自行安装 DSH 并绑定会话，模型与供应商由 DSH 管理。

## 启动

使用 Node.js 24。在 PowerShell 中运行：

```powershell
Set-Location E:\LingFlow
npm ci
npm start
```

若 npm 禁用了依赖的安装脚本，先运行 `node node_modules/electron/install.js` 下载锁定版本的 Electron。运行数据在 `%LOCALAPPDATA%\LingFlow`。默认服务仅监听 `127.0.0.1:47831`，端口可在数据目录的 `config.json` 修改。修改端口后重新加载 DSH 适配器。

独立窗口和 DSH 侧边栏共用这一个本地服务：谁先启动谁托管，另一个直接附着，不会出现第二个工作流循环。也可以在不开窗口的情况下只让侧边栏拉起服务：

```powershell
npm run service        # 等价于 node src/server.mjs，可加 --port 47831
```

## DSH 侧边栏

除独立窗口外，LingFlow 还提供一个 DSH 侧边栏入口（`panel/`，包名 `lingflow-panel`）。它复用同一个服务、同一份数据和同一条投递链。

**它显示的就是独立窗口那一套界面本身**：面板不自绘、不复制，而是把服务提供的同一个页面（`ui/index.html` 及其样式与脚本）嵌进 DSH 的视觉区域，所以两个入口的界面永远一致；以后改 `ui/` 也不必为侧边栏再改一遍。面板宿主用 `/lingflow-panel/api/frame` 返回 302，把框架页指向共享服务，令牌只出现在 Location 头里，渲染层拿不到。被嵌入的页面把 `frame-ancestors` 放宽到「本机 http + DSH 桌面壳的 `dsh-app:` 方案」——DSH 桌面版自己的页面就运行在 `dsh-app://app/` 这个特权协议上，不列这个 scheme，Chromium 会静默拒绝嵌入（表现为白屏），可用 `LINGFLOW_FRAME_ANCESTORS` 覆盖。

LingFlow 页面自己不带的东西都放在它上方的工具栏里（这样嵌进来的页面才能和独立窗口一模一样）：状态灯、刷新、重启服务、独立窗口、诊断。嵌入默认走 `<iframe>`，12 秒没加载完就自动换成桌面壳的 `<webview>`；两种都失败才显示错误卡片。每一步和每次失败都落到 `%LOCALAPPDATA%\LingFlow\panel-client.log` 与 `panel-access.log`，白屏时先看这两个文件。

```powershell
Set-Location E:\LingFlow
node scripts/panel-install.mjs            # 预览 profile 差异，不写文件
node scripts/panel-install.mjs --apply    # 安装/更新（link 方式，不拷贝代码）
# 然后关闭并重新打开 DSH，侧边栏出现 ◈ LingFlow 图标
```

- 只是预览时不会改动 DSH；应用前先备份 profile `package.json` 到 `.validation\panel\`，回执同目录。
- 脚本只写 `dependencies` 与 `dsh.profile.bundles` 两个字段和一个 `node_modules` 链接，不覆盖其他插件、不手写 `cordis.patch.yml`。
- 因为是 link 安装，之后对 `E:\LingFlow` 的改动会同步过来：`ui/` 改动点开/刷新面板即生效；服务代码改动会被状态接口识别，没有启用角色时自动重载并重挂页面，有启用角色时不打断（用工具栏「重启服务」）；`panel/client.js` 与 `panel/index.js` 改动需要重载 DSH——DSH 在启动时按内容修订号登记 client 包，进程内不会重新读这个文件。
- 卸载：`node scripts/panel-install.mjs --remove --apply`。项目数据、票、独立窗口和 DSH 适配器都保留。

详见 [panel/README.md](panel/README.md)。

## 接入 DSH

先启动 LingFlow 以创建独立配置，再将 DSH 适配器加入所用的 DSH 配置层。`scripts/prepare-dsh.mjs` 接收本机 DSH `dsh-tools/lib/index.js` 的绝对路径，生成 `.validation/dsh-setup/cordis.patch.yml`。本机桌面配置的追加入口是 `node scripts/register-dsh.mjs`，默认只写预览。要应用已核对的注册项，追加 `--apply`。保留现有 DSH 配置项。

在工作台点击「添加项目」，输入名称，再点击目录输入框或「选择目录…」，从系统窗口选择已有项目文件夹。项目创建后从空团队开始，在「团队会话」中添加成员。多位主控时，可指定一位接收需求、结果与阻塞通知。缺少审查成员时，高风险票仍等待独立审查。

项目右上角的「删除项目」需要确认。删除会移除该项目在 LingFlow 中的成员绑定、需求、任务和协作记录，保留项目文件和 DSH 会话。

在同一项目目录下为成员分别新建 DSH 会话。在各会话调用 `lingflow_connect` 列出角色，按角色 ID 请求绑定。用户在独立窗口确认绑定后手动开启角色，模型由 DSH 选择。

在「团队会话 → 添加成员」选择提示词预设或直接编辑正文。展开「管理提示词预设」，可以保存当前正文、更新或删除所选预设。创建成员时保存一份提示词副本，之后改动预设不会影响该成员。已创建的成员可点击角色卡上的名称改名。

项目右上角「主控提示词」可编辑项目主控行为规范，也能选择已有主控编辑个人身份。主控、开发和审查在没有自定义身份时继承各自内置说明。主控设置中的「恢复内置」在保存后清除所选覆盖。团队可配置主控、开发、审查、监管和自定义角色。自定义角色沿所选基础职责运行。旧测试、规划成员可续接原责任并保留历史，不再创建这两种成员或派发新票给他们。监管不接任务，只通过项目独立频道向主控转达用户消息，主控沿原消息回复。工作台的「需求与交付」默认按最近登记的冻结规格显示票号、状态、风险和已验收数量，可切换历史版本或全部任务。

每次开启角色时，完整启动消息包含当前项目、目录、成员绑定、身份、工作方式和流程边界。更新成员资料后，下一次唤醒或 `inbox` 会提供新上下文。日常短卡直接写明唤醒原因、关联票和下一步。同一会话有多项待办时合发，完整内容仍可在收件箱查看。上下文压缩或丢失时，可调用 `context` 重读，工具参数用 `guide` 按需查询。身份提示词按成员保存，工作流权限仍由成员类型与原票决定。

直接在 DSH 主控会话描述需求，并指出希望使用的技能。授权执行后，主控用 `lingflow_team approve` 登记依据，从 spec、tickets、planned attempts 推导读写、风险、验证和资源，再用 `dispatchPlan` 登记实施计划。新实施票使用已有提交的 Git 项目作为基线。纯调查和消息任务可用 `dispatch` 提交只读票。工作台的「进行中」「审查与处理」「交付与验收」显示任务和约束。

调度按真实读写、检查输入、独占资源和前置放行。前置可以等技术验证或用户验收。现场发现冲突时，开发先停写再沿原票 `yieldForSchedule`，主控用 `reviseSchedule` 更新依赖和范围，程序保存调整历史并重新排队。已经改动的文件在归属厘清前保留占用。

角色上下文的 `skillFile` 指向仓库内适合该角色的技能。也可以在 DSH 直接说「请读取 `E:\LingFlow\skills\lingflow-to-spec\SKILL.md`，整理后按我确认的范围派单」。项目内技能使用 `lingflow-` 前缀，可直接按路径读取。

成员用 `inbox` 读取短卡和原责任，用 `inspect` 查看详情。开发用 `check` 执行冻结的局部红绿和完整检查，报告需求、实现及直接系统影响。审查员核对实际差异与原始证据，独立找反例。主控核对流程证据，提交免审票独立验收或计划里的必要短探针，再用 `summarize` 登记试用步骤。

责任角色按检查编号提交已授权原票冻结的命令。项目的「后台检查」显示作业记录。程序在项目根目录运行，保存日志、退出码、输入指纹和作业编号。作业启动后可关闭窗口，重开按原编号对账。结果不确定时保留原记录，由用户核对旧进程和资源，再决定是否重跑。多票明确约定同一累计检查时共用一次作业。候选、输入或日志发生变化，会使相应证据失效。命令按当前用户权限执行，测试数据请使用 `LINGFLOW_TEST_DATA_ROOT`。

「团队会话 → 自动巡检」默认开启。巡检结合真实 DSH 回合和当前任务判断，不用任务记录推测模型仍在运行。空闲且责任未收口、或遇到可识别的临时网络和供应商错误时，按原会话有限续接。每段责任最多自动尝试两次。DSH 离线、手动取消、仍在运行、正在等待输入或已有后台作业时，由面板显示具体状态。检查失败沿原票返回证据，巡检不自动重跑失败命令。

## 投递与恢复

- 派单入库、DSH 送达、报告入库分别记录。写操作的 `operationId` 跨超时与重启保持稳定，可用 `operation` 查询原回执。
- 业务通知保存在 LingFlow 收件箱。每个会话同一时刻只有一个未消费的唤醒。只在会话确认空闲、输入队列为空时尝试投递。能观察到后台任务时也暂缓。主动读取收件箱会作废尚未注入的唤醒。
- 桥接按 DSH 会话独立投递，同一会话保持顺序，使用稳定请求 ID 和本地接收账本对账。回执丢失只补回执。接收证据不明确时显示待对账，可在原 DSH 会话手动调用 `lingflow_team inbox` 接回责任。
- 服务重启保留绑定、票和报告，角色恢复为关闭。手动开启后沿原票续接。
- 候选哈希覆盖声明的读写输入。审查、主控汇总和用户验收都校验当时的候选。声明的写入范围用于调度，实际文件权限由 DSH 和宿主管理。

## 验证和边界

`npm test` 覆盖核心闭环、派单幂等、冲突排队、候选失效、角色权限、通知合并和重复投递，也覆盖侧边栏共享服务、令牌持久化、附着/启动、面板代理、框架页重定向、页面 `frame-ancestors`、写路由防跨站、渲染层日志落盘与打开独立窗口（`tests/panel.test.mjs`、`tests/panel-client.test.mjs`）。后者还会把 client 半部的组件**真渲染一次**——在 DSH 里渲染抛异常就等于白屏，所以这条断言比样式检查更重要。`npm run check` 检查语法，`npm run test:desktop` 验证真实桌面窗口。`npm run test:panel-e2e` 在隔离项目里跑两个入口的完整闭环（含「侧边栏嵌入的页面能取到样式与脚本」）；`npm run test:panel-visual` 用隔离 Electron 实例把「侧边栏里的页面」和「独立窗口的页面」放在同一视口截图比对——像素差容差 0.1% 以内，并且标题、DOM 节点数、关键元素的几何位置与计算样式、全部 `--lf-*` CSS 变量都逐项相等才算通过，产物在 `.validation/panel-visual/`（含 `compare.png` 与差异热图），加 `--size 380x820` 再跑一趟侧边栏宽度、产物带 `-narrow` 后缀。比对的是被嵌入的那张页面本身，面板外壳那条工具栏不在范围内。设置 `LINGFLOW_DSH_TOOLS` 为安装包工具定义路径，可额外验证安装包接口兼容性。`.validation` 保存本机测试证据和隔离项目。

工作流核心、DSH 适配器、桌面窗口和侧边栏面板分离。桌面界面由独立窗口承载，侧边栏是同一服务的第二个视图——而且**是同一份界面文件**：面板把 `ui/` 那套页面嵌进来，宿主只负责同源转发、按需拉起共享服务，以及用 `/frame` 的 302 把令牌挡在渲染层之外，因此两个入口同时打开也只存在一条投递链，界面也不会各走一路。服务以 `panel-service.json` 记录面板拉起的进程，只有该进程可以被自动重载；由独立窗口托管的服务不会被侧边栏杀掉。

票详情分别显示当前候选的开发自测和适用的独立审查：需求正确性、实现一致性、直接系统影响，各维显示实际结论和证据。无历史记录时不推断为通过。

LingFlow 或会话意外退出后，打开原会话，在工作台点「开启角色」；已开启时点「续接原会话」。系统等原会话实时显示空闲且没有排队输入后投递一次续接卡，收件箱提供原票、进度、候选、问题和检查索引。重新开启不会创建新票或改动工作区。已完成的检查凭原回执复用；结果不明的检查先对账再决定重跑。若原会话已删除或项目文件已丢失，不能自动还原。
