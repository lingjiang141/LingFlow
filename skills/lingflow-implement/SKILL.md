# 原票实施

1. 用 `inbox` 接回自己的责任，`inspect` 读原需求、验收、读写范围和风险。查看实际 Git 工作区及项目约定。范围不匹配或必要输入缺失时，先沿原票 `question`。
2. 写入票先准备已声明的行为测试，保持实现文件不变。用 `check` 提交冻结的红阶段，按原作业号确认真实断言失败，再做最小实现。依次提交绿与完整检查。长检查提交后可以结束回合，等待结果。只读票输出调查或消息结果。
3. 核对需求正确性、实现一致性和直接系统影响。使用 `checkEvidence` 引用真实作业结果。发现写入冲突时停止写入，`yieldForSchedule` 交回原票，等主控修订后续接。
4. 以 `report` 提交三维证据和已知限制。每项通过结论写明为何成立，并在 `checkIds` 引用本票已通过的实际检查。确认 `stored` 后结束回合。契约漂移沿原票请主控对账；证据缺失先补证据；实测出现反例时记录复现。普通进度用 `progress`，请求超时用原 `operationId` 对账。
